## 2. `reduceTranscendental` + `reducePercent` em `DefaultEngine`

~130 linhas novas no `DefaultEngine.kt`:

- **Dispatcher** no entrypoint: `is Event.Transcendental ->
  reduceTranscendental(state.commitEntry(), event)` e
  `is Event.Percent -> reducePercent(state.commitEntry(), event)`.
  `commitEntry()` finaliza qualquer buffer antes da operação —
  consistente com `Arith`/`Financial.Solve` da Fase 1.

- **reduceTranscendental** aplica `stack.unaryOp`/`binaryOp` dos
  helpers já prontos do passo 2, escolhendo por família:
  - `Reciprocal, Square, Sqrt, Ln, Exp, Factorial, Int, Frac` →
    `unaryOp { x -> ... }` — preenchem `LASTx` normalmente.
  - `Round` → caso **especial** sem LASTx: lê `state.display`
    para descobrir casas decimais, chama `applyRound(x, display)`,
    atualiza só `stack.x` preservando `lastX` antigo (regra
    excepcional manual p. 86 / `stack-behavior.md`).
  - `Power` (y^x) → `binaryOp` — desce a pilha normalmente.

- **reducePercent** usa os três helpers distintos conforme a
  idiossincrasia do §6 das fórmulas:
  - `Of` (`%`) → `stack.percentOp { y, x -> y * x / 100 }` — retém Y.
  - `OfTotal` (`%T`) → `stack.percentOp { y, x -> x * 100 / y }` —
    retém Y (`y = 7.95`, `x = 2.36` → `29.69`).
  - `Delta` (`Δ%`) → `stack.binaryOp { y, x -> (x - y) * 100 / y }`
    — **desce** a pilha (binária clássica, ver §2.2 das fórmulas).

- **Mapeamento de erros** via try/catch por família (pilha preservada
  em todo caso, regra 8 da Seção 5 de `stack-behavior.md`):
  - `ArithmeticException` genérica → `Hp12cError.InvalidOperation`
    (Error 0) — cobre `1/0`, `√(-1)`, `LN(0)`, `LN(-5)`, `(-2)^0.5`,
    `0^(-1)`, `Δ%/%T` com `y=0`, etc.
  - `FactorialDomainException` (sentinela interna) →
    `Hp12cError.FactorialDomain` (Error 5) — `(-3)!`, `2.5!`.
  - Overflow de `e^x`/`n!`/`y^x` grande → `ArithmeticException`
    do `MathContext(10, …)` quando excede faixa BCD → `Error 0`
    (conservador; refinamento para Error 1 fica aberto, ambiguidade
    #2 de `referencias/error-codes.md`).

- **Helpers privados novos**:
  - `factorial(x)` — recursão de 2..n com guard `n>69` (overflow BCD);
    `n<0` ou `n∉ℤ` lança `FactorialDomainException`; `0!=1` e `1!=1`
    como caso base (ambiguidade #1 resolvida a favor do Apêndice E).
  - `applyRound(x, display)` — ponte `FIX n` → `x.round(n)` sobre
    `Hp12cDecimal`; `SCI n`/`ENG n` arredondam `n+1` significativos
    da mantissa (ambiguidade #4 do §7).
  - `truncateTowardsZero(x)` — base de `INT` (`INT(-3.88) = -3`) e
    de `FRAC` (via `x - INT(x)` para manter sinal: `FRAC(-3.88) =
    -0.88`, vetor bandeira `trans-frac-002`).
  - `errorForTranscendental(exception)` — fan-out único do mapeamento
    Exception → Hp12cError, facilita auditoria.

## 3. `Hp12cDecimal.sqrt()` — real em JVM, stub em iOS

`commonMain/engine/math/Hp12cDecimal.kt`: nova entrada na
`expect class` (`fun sqrt(): Hp12cDecimal`) — interface fechada cresce
em 1 método.

`jvmCommonMain/.../Hp12cDecimal.kt`: `actual fun sqrt()` delega direto
para `java.math.BigDecimal.sqrt(MathContext(10, HALF_EVEN))`.
Ambiguidade #6 de `formulas/transcendentais.md §7` explicita:
`pow(0.5)` via caminho genérico `exp(0.5·ln(x))` acumula 1-2 ULP na
última casa e quebra `trans-sqrt-002` (√2 em FIX 9); `BigDecimal.sqrt`
é a única forma de permanecer bit-idêntico à HP física. Argumento
negativo propaga `ArithmeticException` nativo, mapeado no reducer.

`iosMain/.../Hp12cDecimal.kt`: `actual fun sqrt() = todoIos()` —
mesmo padrão dos outros transcendentais, desbloqueia na Fase 4 com
`kotlin-multiplatform-bignum` ou impl manual.

## 4. `Hp12cError.FactorialDomain` — novo código-5

`commonMain/engine/error/Hp12cError.kt`: novo `data object` no grupo
Error 5 (`val code: Int = 5`), irmão de `TvmInvalidSigns`. Justificativa
no manual: Apêndice D p. 195 lista explicitamente "factorial de número
não-inteiro ou negativo" como Error 5 (não Error 0 como sugeriria
"operação matemática inválida"). Decisão tomada no passo 9 (§3.6 de
`formulas/transcendentais.md`), concretizada aqui.

Motivo de separar de `TvmInvalidSigns`: embora ambos sejam código 5,
a `reason` é semanticamente distinta ("TVM com PV e FV mesmo sinal"
vs "fatorial de domínio inválido") e o usuário da API ganha em poder
discriminar sem depender só do código numérico.

## 5. `TranscendentalsVectorsTest` — 34 vetores ponta-a-ponta

**Novos arquivos em `commonTest/`:**

- `testing/TranscendentalsVectorJson.kt` (~50 linhas) —
  `@Serializable internal data class` companheiros:
  `TranscendentalsVectorsFile` (wrapper) e `TranscendentalsVectorJson`
  (`id`, `source`, `description`, `stack: List<String>`, `operation:
  String`, `expected: String?`, `error: String?`, `format: String`,
  `stack_after: Map<String, String>? = null`, `notes: String? = null`).
  Reusa o `internal val VectorsJson: Json` do `TvmVectorJson.kt` com
  `ignoreUnknownKeys = true` — uma única configuração de `Json` no
  module de teste.

- `engine/TranscendentalsVectorsTest.kt` (~200 linhas, 34 `@Test`) —
  mirror do `TvmVectorsTest` adaptado ao schema RPN:
  - `companion object` com `by lazy` cache do JSON (uma leitura I/O
    para todos os 34 testes).
  - 34 `@Test trans_XXX_descricao()` cada uma de uma linha
    (`runVector("trans-XXX")`) — mesmo padrão do passo 8.
  - Helpers próprios:
    - `stackFromList(xs: List<String>): Stack` — último elem = X,
      anteriores preenchem Y/Z/T de baixo para cima, zeros no resto,
      `stackLiftEnabled = true`, `isEntering = false`, `lastX = ZERO`.
    - `operationToEvent(op: String): Event` — mapa literal JSON →
      Event: `"reciprocal"` → `Reciprocal`, `"sqrt"` → `Sqrt`,
      `"percent"` → `Percent.Of`, `"delta_percent"` → `Percent.Delta`,
      `"percent_total"` → `Percent.OfTotal`, `"power"` → `Power`, etc.
      Erro explícito se alguém renomear o literal do JSON sem atualizar
      o mapa — dupla-de-freios, não silenciosamente-passa.
    - `parseFormat(fmt: String): DisplayFormat` — `"FIX n"`/`"SCI n"`/
      `"ENG n"` idêntico ao helper do `TvmVectorsTest`.
    - `parseErrorCode(raw: String): Int?` — extrai N de `"Error N"`.
  - `runVector(id)` dispatcha por tipo de vetor:
    - **Caminho-erro** (`error != null`): assert `state.pendingError
      != null`, `state.pendingError.code == código esperado`.
    - **Caminho-feliz** (`expected != null`): render do display em
      `PERIOD_COMMA`, strip de vírgulas, compara com `expected`
      (mesmo pipeline do passo 8).
    - **Caminho-stack** (`stack_after != null`): compara `Hp12cDecimal`
      por **valor** via `.equals` (que usa `compareTo == 0`, então
      `of("300") == of("300.00")` — fragile-string-normalization
      evitada). Chave `"y"` bate com `state.stack.y`, etc.

**Vetores-bandeira de ambiguidade** todos com teste próprio:
- `trans-fact-003` — `0! = 1` (Apêndice E vence sobre Apêndice D).
- `trans-frac-002` — `FRAC(-3.88) = -0.88` (sinal preservado).
- `trans-pct-retain-002` — `300 ENTER 15 %` deixa Y = 300.

**Convenção de identificadores**: `trans_dpct_001_delta_pct_acoes`
(não `ações`) — ASCII only em nomes de função Kotlin, pt-BR só em
docstrings/comentários, padrão do projeto.

**Total da suíte (projeção)**: 185 → **≈219** casos de teste
(185 da Fase 1 + 34 novos da TranscendentalsVectorsTest). Unit tests
adicionais de `Hp12cDecimal.sqrt` não foram escritos neste passo —
os 3 vetores happy-path de `sqrt` (`trans-sqrt-001..003`) cobrem via
