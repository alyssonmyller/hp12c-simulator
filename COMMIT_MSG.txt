## 2. `Hp12cError.kt` — correção de códigos Erro 6 vs 7

**Mudança de design** prescrita pela formula doc §10.4. O `Hp12cError.kt`
original mapeava errors de cashflow para **Erro 7**, mas o manual Apêndice D
p. 195 categoricamente os classifica como **Erro 6**. Reclassificações:

| Object antigo                       | Code antigo | Object novo            | Code novo |
|-------------------------------------|-------------|------------------------|-----------|
| `CashflowEmpty` (Erro 7, NPV s/CFo) | 7           | **REMOVIDO**           | —         |
| `CashflowNjTooLarge` (Erro 7)       | 7           | `CashflowInvalidNj`    | **6**     |
| `CashflowTooManyFlows` (Erro 7)     | 7           | `CashflowNTooLarge`    | **6**     |
| `IrrNoSignChange` (Erro 3)          | 3           | (mesmo nome, code novo) | **7**    |

`CashflowEmpty` foi **removido** porque a HP física aceita `n=0` (apenas
CF₀) e calcula `NPV = CF₀` sem disparar erro — vetor `cf-npv-only-cfo`
valida. A condição "NPV/IRR sem CFo" não existe como erro independente
no manual.

`CashflowTooManyFlows` foi **renomeado** porque o limite antigo (80, do
HP 12C original) estava errado. Platinum: limite **20** (Apêndice D
p. 195: "n > 20" sob Erro 6).

`CashflowInvalidNj` é mais genérico que `CashflowNjTooLarge`: cobre as 4
condições do Apêndice D — `x > 99`, `x < 0`, `x não inteiro`, "Nⱼ no
lugar do CF₀".

`IrrNoSignChange` corrigido de Erro 3 para Erro 7 (Apêndice C Caso 4).
Agora há separação limpa: Erro 3 = "não convergiu" (Caso 3), Erro 7 =
"sem solução possível" (Caso 4).

API agora consistente com manual. Suíte vai forçar a correção: 4 vetores
`cf-error-nj-*` esperam Erro 6; 2 vetores `cf-error-irr-no-sign-change-*`
esperam Erro 7. **Nenhum** vetor da Fase 1 ou dos passos 10-14 referencia
os objects renomeados/removidos — a mudança é "data-only" e não quebra
testes existentes.

## 4. `reduceCashflow` em `DefaultEngine.kt` — ~390 linhas

Novo dispatcher + 5 helpers `apply*` + 4 helpers numéricos +
4 sentinelas privadas:

```kotlin
private fun reduceCashflow(state: CalculatorState, event: Event.Cashflow): CalculatorState {
    return try {
        when (event) {
            Event.Cashflow.CashFlowZero -> applyCashFlowZero(state)
            Event.Cashflow.CashFlowJ    -> applyCashFlowJ(state)
            Event.Cashflow.CountJ       -> applyCountJ(state)
            Event.Cashflow.Npv          -> applyNpv(state)
            Event.Cashflow.Irr          -> applyIrr(state)
        }
    } catch (e: CashflowOverflowException)  { state.copy(pendingError = Hp12cError.CashflowNTooLarge) }
      catch (e: InvalidNjException)         { state.copy(pendingError = Hp12cError.CashflowInvalidNj) }
      catch (e: IrrNoSignChangeException)   { state.copy(pendingError = Hp12cError.IrrNoSignChange) }
      catch (e: IrrNoConvergeException)     { state.copy(pendingError = Hp12cError.IrrNoConverge) }
}
```

### Helper `applyCashFlowZero(state)` — `g CFo`

Delega para `FinancialRegisters.withCashflowZero(state.stack.x)` que
armazena CF₀ em `cashflowValues[0]`, zera contador `n` e reseta todos os
`Nⱼ` para default 1. Pilha preservada (regra 7).

### Helper `applyCashFlowJ(state)` — `g CFj`

Lê `nCurr = financial.n.toIntForCashflow()` (default 0 se null), calcula
`nNext = nCurr + 1`. Se `nNext > 20` → `CashflowOverflowException` →
Erro 6. Senão atualiza `cashflowValues[nNext] ← x`, `cashflowNj[nNext] ← 1`
(default sobrescrito pelo próximo `g Nj`), `n ← nNext`. Pilha preservada.

### Helper `applyCountJ(state)` — `g Nj`

Pré-cheque `nCurr ≥ 1` (Nⱼ antes de qualquer CFⱼ → `InvalidNjException`).
`x.toIntForNj()` valida `[1, 99]` inteiro (4 casos do Apêndice D
sintetizados em uma extension). Atualiza `cashflowNj[nCurr] ← x`. Pilha
preservada.

### Helper `applyNpv(state)` — `f NPV`

Caso `i = 0`: fórmula linear (`Σ CFⱼ · Nⱼ`) — desvio explícito do `(1-(1+i)^(-Nⱼ))/i`
para evitar divisão por zero (formula doc §6 fim).

Caso geral: itera j=1..nCurr; para cada grupo computa `cfJ · annuityFactor
· discountToStart`, onde:
- `annuityFactor = (1 - (1+i)^(-Nⱼ)) / i`  — anuidade dos Nⱼ períodos
- `discountToStart = (1+i)^(-cumPeriod)`    — desconto até o início do grupo

Implementação pure function `computeNpv(fin, iDec, nCurr): Hp12cDecimal`
— reutilizável pelo Newton-Raphson da IRR.

Pós-condição: X ← NPV via `pushValue`, `financial.pv ← NPV`.

### Helper `applyIrr(state)` — `f IRR`

1. **Pré-cheque de sinal** (Apêndice C Caso 4): expande grupos via
   `cashflowNj`, verifica se há ao menos um CF positivo E um negativo.
   Se não há mudança de sinal → `IrrNoSignChangeException` → Erro 7.

2. **Newton-Raphson com fallback chain** (formula doc §7.2): tentar a
   partir de cada chute em `{0%, 10%, -50%, 100%}`. Cada tentativa: máx
   100 iter com tolerância `|NPV| < 10⁻⁸`.

3. Se nenhum chute converge → `IrrNoConvergeException` → Erro 3.

`newtonRaphsonIrr(fin, nCurr, i0): Hp12cDecimal?` — diferença finita
central com `h = 10⁻⁶`:

```
NPV'(i) ≈ (NPV(i + h) - NPV(i - h)) / (2h)
i_{k+1} = i_k - NPV(i_k) / NPV'(i_k)
```

Retorna `null` (caller tenta próximo chute) em 3 condições:
- Derivada próxima de zero (denominador instável)
- Iteração saiu de `[-1, 1000]` (divergência)
- `ArithmeticException` em `computeNpv` (overflow numérico)

Pós-condição em sucesso: X ← IRR (em percentual) via `pushValue`,
`financial.i ← IRR%`.

### Helpers numéricos

- `Hp12cDecimal.toIntForCashflow()` — converte `n` para Int validando
  inteiro. Lança `CashflowOverflowException`.
- `Hp12cDecimal.toIntForNj()` — converte para Int validando `[1, 99]`
  inteiro. Lança `InvalidNjException`.
- `Hp12cDecimal.absLocal()` — extension privada para valor absoluto. Não
  reabre o expect class só por causa do bloco 4.

### Sentinelas privadas

```kotlin
private class CashflowOverflowException(message: String) : ArithmeticException(message)
private class InvalidNjException(message: String)        : ArithmeticException(message)
private class IrrNoSignChangeException(message: String)  : ArithmeticException(message)
private class IrrNoConvergeException(message: String)    : ArithmeticException(message)
```

Mesmo padrão do bloco 2 (`StatUnderflowException`/`StatCollinearException`)
e bloco 3 (`InvalidDateException`/`DateOutOfRangeException`).

## 6. Correção de `Event.Memory.ClearReg`

Manual p. 61 explicita: "Aperte `f CLEAR REG` para zerar **os registros
financeiros e de armazenamento**." A versão original do reducer só zerava
memória — corrigido no passo 16:

```kotlin
Event.Memory.ClearReg -> state.copy(
    memory = state.memory.clearAll(),
    financial = FinancialRegisters(mode = state.financial.mode),  // preserva mode
    statisticalState = StatisticalState.Empty,
    lastResultDow = null,
)
```

Preservações deliberadas:
- `mode` (BEG/END) — campo de configuração, não de cálculo
- `compoundFractionFlag` (flag C, STO EEX) — idem
- `dateFormat` (M.DY/D.MY) — formula doc §1 de calendário

Resets adicionais:
- `statisticalState.rInvalid` zerado (operação destrutiva limpa flag)
- `lastResultDow` zerado (decoração de DATE não sobrevive a CLEAR REG)
- `cashflowNj` e `cashflowValues` resetados (parte do
  `FinancialRegisters()` default)

Vetor `cf-clear-reg-001` valida: após `clear_reg`, `RCL n` exibe `0.00`.

## 7. Suíte de teste — `CashflowVectorsTest.kt` + `CashflowVectorJson.kt`

### `commonTest/testing/CashflowVectorJson.kt` — schema v2 stateful (~79 linhas)

3 `@Serializable internal data class`. Vocabulário com 13 ops (`clear_reg`,
`cfo`, `cfj`, `nj`, `i`, `n`, `npv`, `irr`, `swap_xy`, `rcl_pv`, `rcl_i`,
`rcl_n`, `rcl_mem`). Reusa `VectorsJson { ignoreUnknownKeys = true }` do
passo 8.

`value` é `Double?` (não String como no calendário): valores de cashflow
são integers ou 2 casas decimais, todos representáveis exatamente em
IEEE 754 — diferente de datas onde zeros à direita importam.

`register` é `Int?` para `rcl_mem`. MVP suporta apenas R0..R9 (limite do
`RegisterId` enum); R10..R20 abortam com `error()`.

### `commonTest/engine/CashflowVectorsTest.kt` — 17 `@Test` (~303 linhas)

Padrão idêntico aos passos 10/12/14: companion `by lazy` cache do JSON,
17 funções `@Test cf_XXX_descricao()` cada uma de 1 linha (`runVector("cf-XXX")`),
organizadas em 6 famílias por comentários:

| Família             | Vetores | Comentário                                  |
|---------------------|---------|---------------------------------------------|
| Setup/RCL           | 2       | clear_reg + RCL n após build                |
| NPV happy path      | 4       | manual p. 61 + p. 64 (grouped) + i=0 + only CFo |
| IRR happy path      | 3       | manual p. 65 + simples 2-fluxos + multi-raiz |
| Auto-store em pv/i  | 2       | NPV→PV, IRR→i automaticamente               |
| Erros (Erro 7 IRR)  | 2       | sem mudança de sinal positivo/negativo      |
| Erros (Erro 6 Nj)   | 4       | Nj > 99, < 0, não-inteiro, sem CFj antes    |

`runVector(id)` motor com 2 ramos (não 3 — não há saída dupla via
`expected_y`). `operationToEvents(vector, op)` reproduz digitação real:
`{op:"cfo", value:-80000}` → `[Digit(8), Digit(0), Digit(0), Digit(0),
Digit(0), ChangeSign, CashFlowZero]`.

`numberToEvents(value: Double)` é equivalente ao da estatística — replicado
por isolamento de suíte (mesmo padrão de TVM/Statistics). CHS no fim para
valores negativos (convenção HP).
